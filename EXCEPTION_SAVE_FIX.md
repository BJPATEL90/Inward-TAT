# Exception save responsiveness — 26 October 2026

The screenshot showed multiple rows indefinitely in Saving state. Code inspection confirmed exception writes had no browser deadline, so a stalled fetch or JSON response never settled the row's saving state. Each backend save also waited up to 30 seconds for the shared pipeline lock, re-ran schema/header formatting and read all 29 columns of every fact. These amplify latency under concurrent saves or pipeline work. The screenshot alone does not establish which network/server event stalled those particular requests; no invented production save was made to reproduce it.

Changes:

- Exception saves use a 45-second confirmation deadline covering both fetch and response-body parsing; the browser aborts its request when the deadline expires. A server execution already started may still complete. The message explicitly describes that uncertainty, retains the row draft and enables retry. Exception writes have one transport attempt, not three automatic attempts. Other calls retain their existing retry count and no new deadline.
- Backend saves use a bounded five-second shared-lock attempt. A busy pipeline/save returns an actionable retry error before any transaction write. The same script lock still protects the row position from normal pipeline rebuilds.
- A save verifies the existing 29-column header, reads only the stable-key column and then the matched physical row. It no longer applies formatting or transfers the full fact matrix. Duplicate/missing keys, stale edits, permissions, KPI eligibility, formula-safe text, WH=N rules and cache invalidation remain enforced. Only AA:AC are written.
- Retrying identical desired saved values is accepted even if the expected baseline is old (lost confirmation). Different concurrent values still fail stale-edit validation. Rows and saved KPI averages change only after a successful acknowledgement.

Tests: new transport VM checks stalled fetch, stalled JSON body, abort, timer cleanup, no automatic write retry, successful response and permission failure. Browser regression advances the clock through a stalled save and verifies the exact draft survives, an error appears and Save is enabled. Backend tests verify idempotent retries, true stale conflicts and lock contention with no write. Existing exception CSV/XLSX, monthly ingestion, Apps Script syntax, hybrid matching, reminder, lint and build checks pass. The existing lazy ExcelJS large-chunk build warning remains.
